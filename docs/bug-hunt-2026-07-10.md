# CKast Deep Bug Hunt — 2026-07-10

## Scope and baseline

Reviewed the complete maintained code surface: `pc-broadcaster/server.js`, all files in
`pc-broadcaster/lib/`, the dashboard, the Tizen receiver, launcher and packaging config,
tests, documentation, current working-tree edits, and the latest synchronization commit.

Baseline evidence before repair:

- 28/28 existing tests pass.
- Every JavaScript file passes `node --check`.
- Production dependency audit reports zero known vulnerabilities.
- Existing tests do not execute `server.js` or `mpvController.js`; Tizen runtime tests are
  regex assertions rather than behavioral tests.

No production fixes were made during discovery.

## Confirmed findings

### A. Stream/session ownership failures

1. **Desktop and file encoders can run simultaneously and write incompatible fMP4
   streams to one MSE pipeline.** `startCapture()` does not stop `fileVideo`. A live API
   reproduction reported `desktop=true` and `fileActive=true` after switching modes.
2. **A pending synced-resume timer survives a switch to desktop capture.** The timer later
   sends `play` and starts MPV in the new mode. Live reproduction showed
   `pendingAfterDesktop=true` and a late `play` control.
3. **File-player controls are sent to the TV even when file video is not the active TV
   mode.** Play, pause, seek, and stop can pause or clear a desktop-capture pipeline.
4. **Desktop Stop does not send a TV stop/reset control.** A WebSocket trace contained
   `fixedLatency`, `fixedLatency`, `reset`, but no `stop` after `/stop`.
5. **Reconnect has no authoritative session handshake.** When a TV connects during a
   desktop stream, the server sends only `fixedLatency` plus binary fragments—no `reset`
   carrying `mode=desktop`. The TV remains in `idle` mode and its controller cannot start.
6. **Reconnect retains stale telemetry and desktop timing baselines.** A new TV pipeline
   can be controlled using the old pipeline's current time and buffer measurements.
7. **Superseded TV sockets remain active telemetry producers.** After connecting two
   clients, the first client could still overwrite `tvSyncState` and drive synchronization.
8. **The file-to-desktop control order disables fixed latency.** The server sends the
   desktop fixed-latency message while the TV is still in `file` mode; the TV deliberately
   forces fixed latency off in file mode, then the following reset changes the mode without
   restoring it. The receiver harness reported `playbackMode=desktop, enabled=false`.

### B. Process lifecycle failures

9. **Desktop FFmpeg close leaves a dead process object marked as running and disables the
   watchdog.** Killing the owned FFmpeg process produced `reportedRunning=true` with
   `actualFfmpegCount=0` six seconds later.
10. **The desktop watchdog is not armed until the first init/segment event.** Startup hangs
    and pre-initialization failures are never recovered.
11. **A stale desktop FFmpeg close event can clear the watchdog belonging to a replacement
    process.** The handler is not generation/process guarded.
12. **Desktop capture ignores `FFMPEG_PATH`.** File streaming uses the configured path,
    while desktop capture always spawns the literal `ffmpeg` command.
13. **MPV stop/open has the stale-process race already fixed in FileVideoStreamer.** A rapid
    stop/open diagnostic left eight orphan MPV processes and failed to complete.
14. **MPV IPC connection failure leaks the spawned process.** Using a valid executable that
    never creates the pipe returned an IPC timeout while status still reported
    `running=true, hasProcess=true`.
15. **Unexpected MPV exit/socket close does not reject pending commands immediately, and
    the IPC parse buffer is not reset between processes.** Requests wait for timeout and a
    partial old message can corrupt the next session.
16. **Server shutdown has no child cleanup.** MPV can survive server restarts. The launcher
    also kills every `server.js` Node process and every PID matched by `:8080`, including
    unrelated processes or remote-port matches.
17. **MPV is not audio-only.** The live command line contains `--force-window=yes` and no
    `--video=no`, contrary to the synced-player contract.

### C. File pacing, readiness, and backpressure failures

18. **File FFmpeg is unpaced.** A 12-second fixture was completely encoded in 0.827 seconds
    (about 14.5x real time). This bursts the whole movie toward the TV.
19. **The encoder normally ends before the five-second synchronized start.** Once
    `fileVideo.active` becomes false, `handleTvSyncState()` refuses to calculate drift even
    though the TV is still playing buffered video. A live trace showed `mode=ended`, no
    `fileSync`, and no reported drift.
20. **Synchronized start is a blind timer, not TV readiness.** The server sends `play`
    without receiving any TV telemetry or proving an appended buffer exists.
21. **Options and video-offset restarts reset TV video without pausing MPV.** A live
    reproduction showed `afterPaused=false` while `pendingResume=true`; audio continues
    through the rebuffer interval.
22. **There is no backpressure contract.** `ws.bufferedAmount` is ignored, segment stats are
    dead data, and the receiver queue has no bound.
23. **The receiver retains 60 seconds of decoded source history and only evicts every 20
    seconds.** At the desktop default of 20 Mbps that is at least 150 MB before overhead;
    an unpaced file can fill future buffer far faster. Quota handling can requeue forever
    when current time is too low to evict.

### D. Receiver asynchronous state failures

24. **Pause before the first append can autoplay later.** `pause` does not clear
    `shouldAutoPlay`. The receiver harness observed playback restart after pause when the
    first binary chunk arrived.
25. **Stale MediaSource callbacks act on the newest global MediaSource.** An old
    `sourceopen` after reset attempted `addSourceBuffer()` on a new, unopened instance and
    produced `ERROR: MediaSource not open` in the harness.
26. **Old SourceBuffer callbacks are also unscoped.** An `updateend` from a replaced buffer
    can process the new session's queue.
27. **`sendSyncState()` does not handle a socket closing between the ready-state check and
    `send()`.** This produces uncaught periodic errors during disconnect races.

### E. Timing and validation failures

28. **Mirror-lag math compares different time origins.** It subtracts TV elapsed since the
    first telemetry sample from capture elapsed since encoder initialization. With capture
    elapsed 10 seconds and TV current time 9 seconds, a TV base of 4 makes it report 5
    seconds instead of the actual 1 second. The stored baseline receive timestamp is unused.
29. **Missing fixed-latency measurements are coerced to zero.** With actual lag 3 seconds
    and missing buffer telemetry, the helper incorrectly shrinks the TV target to 0.35
    seconds instead of waiting/falling back.
30. **Explicit file start time zero is ignored.** `Number(startTime) || currentTime` treats a
    valid zero as absent.
31. **Subtitle timelines are wrong after seek/restart.** Starting the stream at source time
    6 seconds failed to render the cue active at 6 seconds, then rendered the cue from
    source time 1 second at output time 1.2. This affects external and embedded subtitles.
32. **Subtitle setup failure leaves FileVideoStreamer in a false `starting` state.** A
    missing delayed subtitle returned an exception while status retained the media path,
    starting mode, and no error.

### F. Dashboard and observability failures

33. **Status polling can overlap indefinitely.** Each poll can issue six MPV IPC commands;
    there is no in-flight guard when MPV is slow.
34. **Polling overwrites actionable operation errors and transient state.** Several action
    handlers also lack `try/catch`, leaving controls stuck on request failure.
35. **Reported stream status is not authoritative.** Desktop uses object presence rather
    than child liveness, file `ended` disables sync too early, and the unused segment stats
    provide no congestion visibility.

## Root-cause correlations

The findings reduce to five shared causes:

1. **No single owner for the TV stream session.** Mode, generation, socket, encoder,
   telemetry, and pending playback are stored independently.
2. **Async resources are identified by mutable globals rather than generation identity.**
   This causes stale process, socket, timer, MediaSource, and SourceBuffer callbacks.
3. **File transport has no clock or flow-control contract.** FFmpeg runs as fast as possible,
   readiness is time-based, and queues are allowed to grow.
4. **Restart behavior is duplicated across routes.** Start, seek, options, nudge, reconnect,
   and mode switch each perform a different subset/order of pause, reset, encode, readiness,
   and resume.
5. **Tests cover pure math but not the orchestration that fails.** The most stateful files
   have no behavioral coverage, and the receiver is tested textually.

These causes define the repair order: lifecycle primitives first, then one authoritative TV
session/restart path, then paced readiness/backpressure, then receiver generation guards and
timing corrections, followed by dashboard/launcher hardening.
